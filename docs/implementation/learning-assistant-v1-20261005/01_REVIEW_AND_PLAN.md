## 一、结论

下一步先做“总结辅导 + 实践 Prompt 辅导”两种会话，而不是先消耗额度重新生成完整路线。

产品边界不扩张：开始总结／开始实践 → 创建新会话并打开右侧助手 → 评价、追问、修改工作稿 → 用户明确保存正式总结／Prompt → 主体显示正式结果。会话不依赖 RAG。

这不是纯前端搬家：原评审服务绑定正式提交且每份提交只对应一条评审运行，不能直接承担保存前的多轮辅导。需要最小会话持久化与单轮任务接线；不需要新的 Agent 平台、长会话 Graph、向量记忆或第二队列。

## 三、需要修正或补足的产品决定

### 1. “先保存原文”分为两种保存

- 点击发送：先把用户消息／工作稿保存到会话，再请求模型。这是防丢失，不是正式总结或 Prompt 提交。
- 点击“保存为阶段总结”或“保存为任务 Prompt”：把用户确认的精确文本交给原保存服务，产生正式修订。

聊天、助手赞同、会话结束，都不能成为阶段完成或实践验收依据。用户不必得到 AI 认可才能正式保存。

### 2. “修改我的稿子”与“追问”必须区分

同一个输入框支持两种明确意图：提交／更新工作稿，以及追问。第一次默认工作稿，之后用户可明确切换。

“为什么这里不对？”属于追问，不应覆盖上一份总结或 Prompt。服务端保存当前工作稿所对应的用户消息 ID；助手回复也绑定它实际评价的版本。

最终保存的小编辑区默认填入用户工作稿，而不是最后一条聊天或整段 AI 回复。用户主动采用建议后再保存，不能自动拼接对话生成“用户原文”。

### 3. 两个开始按钮创建新会话；打开历史只恢复

每次明确点击开始总结／开始实践，创建一条新会话。双击、同一个请求重传只能创建一次。普通侧栏开关、切换页面、刷新、打开“我的会话”不创建新会话、不发模型请求。

总结绑定阶段；实践绑定用户点击的具体 task。没有实践任务时不凭空创建任务。一个阶段多任务时不静默取第一项。

### 4. 会话绑定固定位置，不跟着页面漂移

会话冻结 `actor/project/plan/revision/stage/mode/task` 及必要评审依据。用户切换主区阶段，仍在原会话讨论原目标，顶部清楚显示。

首版旧 Plan 被新版本替代后，会话保留只读；不自动迁移到新 Plan。进行中的回复仍归原消息；不能覆盖当前阶段。正式保存复用原服务的 current-plan 与 CAS 校验。

### 5. 真正多轮，而不是旧评分卡换位置

总结：覆盖、遗漏、明确误解、修改方向；追问时解释原因和例子。

实践：检查用户 Prompt 的目标、输入、约束、范围、输出和验收缺口；说明具体怎么补，但不扩大正式任务。

用户提交改稿后，应能指出哪些旧问题已补上。不要反复输出同一张泛化清单；不增加分数、掌握度、自动验收或自动改计划。

### 6. 主体减负，但不删除已有正式能力

主区保留目标／资源／任务要求、正式总结与 Prompt、版本／历史、导出、成果与 USER 决定。新的互动评审在侧栏完成。

旧已保存反馈仍可在历史详情中读取或由“查看历史反馈”打开；不强行迁移成伪造聊天，也不把它们删掉。直接编辑保存正式原文作为折叠的非 AI 路径保留，模型不可用不能剥夺用户保存能力。

### 7. 模型上下文有限且诚实

仅当前阶段／任务的必要要求、用户明确提供的工作稿、当前追问和有界同会话历史。优先复用现有隐私投影。

资料标题或章节索引不是资料正文。没有读取正文或执行项目时，不得声称“根据该教程全文”或“你的代码已验证”。用户提供的 Prompt 是被评审材料，不是助手执行命令。

### 8. 不把前面的“禁止迁移”继承到新功能上

新会话需要真实持久化，所以允许本功能必需的增量 API／DTO、最小数据表、下一条未占用迁移，以及新 assistant purpose／job 分派。旧公开接口仍须兼容。

最终发布要升级到实际最新 migration head，不再写死“到 0024 就完成”。这是会话功能的必要成本，不是平台扩张。

## 四、最小实现

新增一个封闭的 AssistantService，两种 mode，单轮模型请求一次。按项目当前模式复用 `ai_runs/ai_jobs`、Worker、模型配置冻结、PgAttemptLLM、短评审执行器、鉴权与原文保存服务。

新增持久化仅覆盖：会话、消息／工作稿身份、运行绑定与幂等回执。不要为凑“两张表”把事务责任藏起来，也不要泛化成 chat platform。

新回复协议建议一个有界非空字段 `reply`，Markdown 文本由前端安全渲染；总结／实践模式的评审要求在固定提示与输入中区分。旧 SummaryReviewV1／PromptReviewV1 不改。技术验收之外要检查真实回复是否针对用户文本提出具体修改方向。

每次模型回复独立入队；不让一个 Graph 长期等待用户。暂不做流式输出、工具调用、附件上传、会话向量检索、自动整稿、对话分支、消息编辑删除或额外学习模式。

## 五、执行顺序和收费计划

### 顺序

1. 短基线核对与新接口冻结；只读必要符号和最近报告。
2. 会话／消息持久化、原文与正式产物隔离、原保存服务接入。
3. 单轮助手任务、两种辅导提示、预算／回执／取消及恢复。
4. 两个开始按钮、侧栏、工作稿／追问、我的会话；撤掉主区重复 AI 面板。
5. 新 owned PG、真实 API／Edge、跨账号／版本／失败矩阵、迁移与恢复增量验证。
6. 全非收费门禁通过后，最多 6 次助手真实回复：两种模式各“初稿→追问→改稿再评”三次。
7. 汇总结果并 STOP；此时再由用户批准或通过正常 UI 明确发起一条全新的本人规划 Run。

前面各非收费切片在同一个 Goal 内连续执行。同因缺陷一次做完整反例矩阵、一次复核，不为每个断言单开评审。无需重新研究三个参考项目或再次抓取教材。

### 新额度

用户在原累计上限 200 上增加 80：新上限 280。当前已记录已用 160，理论剩余 120。实际开始时须读账核对；授权只登记一次，不能把“重发同一 Goal”算作再次加 80。

| 用途 | 预算上界 | 授权边界 |
|---|---:|---|
| 本批非收费实现与验证 | 0 | 连续执行 |
| 本批助手真实功能验证 | 6 | 全非收费 PASS 后，只在新 owned 合成会话中执行；不重试未知结果 |
| 后续唯一本人完整规划 | 39 | 仍需本人明确新提交；本 Goal 不代为创建 |
| 两项均按上界后的余额 | 75 | 280 − 160 − 6 − 39；不是要求消费完 |

本包 Active Goal 包含门禁通过后最多 6 次助手收费验证。不改变 model/cap，不增加规划 repair2；无本轮获准真实输入的私人原文外发。额度授权不是正式库写入、部署、push/merge 或用户主观接受。
