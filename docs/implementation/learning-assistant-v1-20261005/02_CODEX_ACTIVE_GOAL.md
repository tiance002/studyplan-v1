## 1. 产品验收目标

### 1.1 两种入口

- 阶段上的「开始总结」：创建新 summary 会话，绑定当前已发布 Plan/阶段，打开侧栏。
- 具体正式实践任务上的「开始实践」：创建新 practice 会话，绑定精确 task/阶段/Plan，打开侧栏。它是 Prompt 辅导入口，不等于执行任务或验收任务。
- 开始按钮由明确用户动作触发；双击/重传同一操作只创建一次。下一次明确开始允许新会话，不强制唯一会话覆盖旧会话。
- 原顶部「学习助手」只展开／收起当前会话；“我的会话”重新打开已有会话；两者不创建会话、不调用模型。
- 没有已确认 Plan/合法 stage/task 时显示原因，不凭空生成上下文；多任务不默认挑错task。

### 1.2 侧栏承担交互

总结模式：根据当前学习要求和用户总结指出已覆盖、遗漏、明确误解、优先修改方向；可以解释“为什么”、举例、审阅用户改稿。不能凭总结宣称已掌握或已验证。

实践模式：评价用户给出的 Prompt，检查目标、输入、范围、约束、交付物和验收是否明确；指出具体缺项及修改方法。不得把建议自动变成新正式任务或强制用户照搬参考项目。

首版必须有真正多轮；不得把旧单次反馈卡放进侧栏就宣称完成。也不得加入泛聊天、第三模式、自动出完整课程或新评分体系。

### 1.3 主区保留事实与正式产物

保留学习目标/知识/资料、实践要求、正式总结/Prompt当前版本、历史、导出、成果/USER决定/Outcome。新AI互动不在主体重复展开。

历史反馈按真实旧记录保留，可折叠或从链接打开；不删除、不伪造为新会话。原直接编辑／保存作为折叠非AI路径保留。无需为此全面重排前端。

## 2. 消息、工作稿和正式保存必须分离

### 2.1 先存会话原文，再取反馈

用户点击发送时，先持久化其精确原文及明确意图，然后才能派发模型。业务保存失败不得派发。模型配置不可用、预算不足、provider失败时，已保存原文仍可读、复制和用于正式保存。

原文保持换行/空白；校验非空不能以trim后的文本覆盖用户原文。客户端不提供可信role、actor、评分、verified或run状态。

本轮严禁将每条消息调用 SummaryService.save/PromptService.save 来“获得评审入口”。这会污染正式修订及阶段完成。

### 2.2 区分工作稿与追问

显式两类用户消息：`work_draft`（提交/更新完整工作稿）、`question`（追问）。命名可适配，但语义不能交给模型猜。

- 第一条默认work_draft，用户可以切换。
- work_draft保存成新不可变消息，并推进当前工作稿指针。
- question不能覆盖工作稿；必须关联当时正在讨论的稿件或明确的回复。
- 回复绑定触发消息、当时work_draft、上下文hash与Run。
- 用户在等待回复时继续编辑不能被迟到回复覆盖。消息不原位改写；新稿产生新消息。
- 开始时可由用户选择带入当前已保存的正式版本作为工作稿；精确绑定所选修订，显示来源，不自动带入全部历史或再次派发旧review。

### 2.3 正式保存

侧栏有「保存为阶段总结」／「保存为任务 Prompt」。打开小编辑区或沿用现有编辑控件，默认内容为用户工作稿，不是最后追问或AI回复。

正式保存不调用模型，不以AI赞同、评分或最后一次回复成功为前置。用户明确确认文本后，调用原 Summary/Prompt 保存服务及原CAS/幂等/版本校验。

新服务只编排：从会话推导精确位置，复用旧保存逻辑，返回正式attempt/revision标识。不能复制一套正式原文表或第二套完成规则。

同一个保存操作响应丢失后必须按原幂等键查回原结果。若正式保存已成功、会话链接或工作区刷新失败，显示“已保存，关联/刷新待核对”，不得二次制造正式修订。会话到正式修订的链接是来源关联，不是第二事实源。

CAS409保留本地工作稿，显示当前正式版本；不得偷偷重新取version并覆盖别人/另一个窗口的内容。旧版Plan禁止向当前Plan误存；用户可复制文本并明确在新版重新开始。

聊天与AI回复不写Summary heads、task accepted、Knowledge VERIFIED或Exposure完成。保存总结仅按既有完成规则参与计算；保存Prompt不是实践验收。

## 3. 最小持久化、API与兼容

### 3.1 所需最小事实

Conversation：会话ID、owner/project、mode、plan/revision/stage、practice task（summary为空）、固定评审依据快照/hash、当前工作稿标识、版本/时间。

Message/Turn：不可变用户/助手原文、会话内有序序号、消息意图、reply_to/工作稿标识、单轮Run引用、输入快照或可重建绑定、创建时间。

幂等回执／运行绑定按当前项目模式落地。可用最小附表；不以“两张表”作为硬限制，也不开发通用消息平台。唯一约束、scope外键及RLS必须覆盖新行与运行绑定。

### 3.2 必需操作

创建会话；有界列会话；有界读取消息；保存用户消息并请求一次回复（实现上可分两步）；读取/取消回复任务；明确保存工作稿为正式产物。

旧接口输入输出语义不改；新增OpenAPI类型由现有流程生成。不要把消息塞到Summary字段、Plan.extensions、ai_runs错误字段或全局localStorage里代替会话表。

新数据只在owned库部署。启动时核对当前迁移head，使用下一未占用编号；不得改已发布0024。新表/新Run kind若需要修改claim函数或CHECK，使用增量迁移并保留原ACL/owner/security属性。最终发布head会因本功能前移，后续正式操作文档按实际head更新，不能继续写死0024。

### 3.3 权限与版本

所有操作校验登录身份、project owner、conversation归属、Plan/stage/task成员关系。ID不能代替授权，客户端title不参与绑定。

会话上下文不随主区导航变化。新Plan替代旧Plan后，旧会话可读但不能继续发新模型请求或正式保存；进行中的回复仍归旧会话，不写当前位置。新会话必须由用户明确开始，不自动迁移。

每会话最多1个未结束回复；新assistant任务纳入原同actor/project评审并发限制，不通过多开会话绕过。对相同目标存在unknown/待核对回复时，按照已冻结scope规则阻止通过新会话或新键自动重派；不能清unknown换ID续费。

## 4. 模型执行：复用基础设施，不复用错误语义

### 4.1 新的封闭用途

新增一个清楚命名的assistant turn用途/协议，两种mode共享。示意 `assistant.coach` / `assistant-coaching-v1`，落地名称一次冻结。

复用当前模型设置解析、冻结配置、PgAttemptLLM、ai_runs/ai_jobs、标准Worker、guard/fence与短review执行器。composition增加一个明确分派；不能伪装成`plan_generate`，也不能裸HTTP绕开账本。

现有Summary/Prompt的上下文投影与评审标准可复用或小幅提取；旧正式评审仍按其原协议读取。不得直接把聊天稿伪造成正式attempt让旧绑定接受。

### 4.2 一条用户请求最多一次模型调用

开会话、欢迎语、读历史、恢复页面、保存正式原文：0次。

一次“发送并获取建议”最多一次provider调用；每turn独立冻结模型引用、schema/协议、输入hash、output cap和max_requests=1。上限不高于现有review output cap。输入边界在派发前检查。

建议新回复合同仅 `{"reply":"非空、有界的Markdown文本"}`，严格JSON解析，不新增复杂评分结构。总结/实践具体反馈标准写在该mode固定提示中。渲染不执行HTML/脚本/命令，不允许模型回复触发工具或业务保存。

本轮assistant reply不继承planning.batch repair2，不自动repair或重试。回复不合格则该turn失败、保留原文；不是重新开启一条39请求规划。旧Known Invalid JSON批次修复保持原范围。

### 4.3 原文、同意与上下文

明确显示发送范围：本次用户消息、当前工作稿、当前阶段/任务要求和限定的同会话历史，将发给已配置模型。按既有consent模式落实，不用创建会话作为外发同意。

当前Goal/Plan或其他私人正文不因“全都在本地DB”就自动外发。复用 `review_rubric_context` / `prompt_review_context` 的白名单思想；必要扩展字段须在用户可见范围中说明。模型看不到其他会话、其他项目、全部总结历史、凭据或私有来源全文。

每次入队冻结完整必要输入；Worker执行不得转读“此刻最新工作稿/当前页面阶段”替换提交依据。历史采用有界最近窗口，建议最多6个已完成问答轮次；最新完整工作稿和当前问题不能静默截短。去除重复携带的同一工作稿，超限派发前明确拒绝或提示缩短，不自动用模型总结历史。

用户Prompt是评审对象，不是给助手的执行指令。没有资源正文、代码运行、成果验证时，回复不能声称拥有这些证据。建议不是新的强制任务或正式验收规则。

### 4.4 计量、unknown、恢复

消息+入队具备幂等；相同key同输入返回同结果，异体409。provider dispatch前有durable attempt和预算，已保存结果恢复不再次dispatch。未知结果进入reconciliation_required，不以浏览器超时当“可以重新发”。

模型返回持久化后、回复消息落库前崩溃：复用同一回执写同一assistant回复，不能重复回复或计费。回复消息与Run结束状态须保持一致或可确定恢复。不得在失败消息里伪造AI成功回复。

注册新purpose/kind时连同ledger协议分支、request_options、SHAPES、claim/submission分派、active-count、取消、status_url一并有界核对；不要只改前端或只给factory传manifest便称完成。保留旧规划/总结/Prompt payload与fingerprint兼容。

## 5. 前端接线和减负

把会话控制器放在不会因收起侧栏就销毁的位置（AppShell上层/现有状态容器均可）。仅保留局部状态，不加全新全局状态框架。

两个开始按钮发明确assistant intent：scope/mode/task及操作key。关闭侧栏不取消运行，不丢工作稿；返回“我的会话”仍能查看消息和已保存稿。退出登录或切换账号清除内存中的私有会话/编辑缓存；重新登录仅按当前身份读取。刷新恢复服务器已保存消息；未发送编辑采用现有缓冲/离开提示，不把长期私人正文无差别放全局localStorage。

顶部固定显示模式、阶段、任务、路线版和所评稿件；页面切换时不变，旧版有标志。晚到响应按conversation/message/sequence归位，不能写入另一个会话。

界面明确区分：正在保存原文、已保存待反馈、生成中、成功、失败、待核对。后台terminal后不能继续显示“等待生成”；轮询读失败保留状态并提供GET刷新，不自动POST新任务。

“我的会话”只实现summary/practice列表、重新打开、分页。标题由阶段/task确定性产生，不为标题花模型请求。首版不做搜索、删除、分支、附件或一般咨询模式。

保留现有侧栏调整宽度；窄屏能打开为抽屉/覆盖面板即可，不重做整体布局。键盘焦点/关闭返回和未保存保护一起测试。
