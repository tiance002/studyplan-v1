## 二、不能破坏的规则

| 检查 | 必须成立 |
|---|---|
| 权限隔离 | 列表、详情、消息、工作稿、run状态、正式保存分别证明跨账号/跨项目拒绝；不能只看前端 |
| 实际app-role | 数据隔离测试不用superuser/BYPASSRLS结果冒充应用RLS通过 |
| 客户端伪造 | actor、role、task跨Plan、来源快照、model_ref、output cap、run状态等不能成为可信输入 |
| 原文归属 | AI回复不能自动作为“用户原文”；用户主动采纳后的正式文本仍不代表实践已执行 |
| 阶段完成 | 仅聊天/反馈/Prompt保存均不新增完成事实；正式总结与实践USER决定沿原规则 |
| 正式历史 | 旧Summary/Prompt/feedback/export、旧Plan/来源/failed/unknown字节或业务事实保持 |
| 单轮预算 | 新assistant用途必带有效冻结manifest；无manifest/错误purpose/schema/model绑定派发前拒绝 |
| 并发 | 同会话一个活动回复；新用途纳入已有project/actor活动限制；取消/迟到结果受fence保护 |
| 单次计费 | 同键同输入重用；异体冲突；成功回执后崩溃不再次HTTP或重复保存assistant消息 |
| 未知结果 | 不通过换会话/换key自动重派相同未核对请求；保留reconciliation |
| JSON范围 | 助手坏JSON失败保原文；不自动继承planning的repair2；原batch修复回归继续通过 |
| 提示注入边界 | 用户Prompt、教材元数据或旧回复中的“忽略要求/改状态/执行命令”只是材料，不能触发工具或业务写入 |
| 输出安全 | 文本/Markdown不执行HTML/脚本/命令；无来源正文不能声称引用正文，无执行结果不能声称项目通过 |
| 上下文边界 | 最新完整稿不截短；只取当前scope、固定要求与有限历史；超限在派发前处理；不外发其他私人内容 |
| 新迁移 | 只新增版本；旧接口不变；不改已发布迁移；新会话持久化/恢复与RLS均实际核对 |

## 三、六次真实回复的内容检查

两个mode各三次，仅在前面门禁均通过后运行。测试原文是自建合成内容，不使用本人未授权的私人总结或Prompt。

| mode | 第一次 | 第二次 | 第三次 |
|---|---|---|---|
| summary | 对照明确学习要求，指出预置的关键遗漏/错误，给一到三个优先修改方向 | 针对同一问题解释原因/例子，不忘记当前稿，不强制生成额外工程任务 | 读改稿并识别已纠正内容，剩余问题与实际文本相符 |
| practice | 对照task指出预置的范围、约束或验收缺项，不擅自改变正式任务 | 回答“怎样修改这条Prompt”等追问，不冒充已执行Prompt | 看见用户补全项，不重复声称仍缺同一条，说明仍有的实际问题 |

每次记录message/工作稿/Run/attempt绑定、输出原文、usage、退出状态和费用账。内容检查是一组代表案例，不证明任意用户问题都必然正确。

遇到known失败停止本收费批次先离线归因；unknown立即按原规则核对，不补跑到6次。第一组通过不重复。
