# 用户验收：不看内部测试数字，只看学习路径是否真的成立

验收对象必须先标明：Fake生成／真实provider生成、Pack版本、Plan版本。未展示的阶段不得算已交付。

## 1. 从路线首页看清楚四段

对“系统学习Agent，主要深入RAG”的样本，页面应能直接找到：

- 公共基础：包含Framework与MCP，不仅是术语；
- 一个小／中型开源核心学习段，能看到候选地址与学习问题；
- 若干RAG专项教程阶段，而不是一句“之后学RAG”；
- 独立的成熟工程切片与迁移验证。

四段内容不能都藏在A8一张项目卡里。我的持续实践项目应贯穿它们，不被迫另做资料工作台。

## 2. 打开A2，确认“会分课”而不是“会新增知识”

同一受控知识能力下面，能看到多个具体学习单元及其目的。例如职责、权限、错误／审计分别讲清楚，而不是只有“组件化与受控行动”一句话。

这些单元不应突然要求学完整K8s、训练模型或安装无关组件。单元多了，不应让我重复提交几套相同验收。

## 3. 打开Framework和MCP

Framework：有一个明确主学框架和一次实际应用练习；其他框架是比较维度与边界，不是各做一遍。

MCP：不止教程链接，应有使用已有server、最小server/协议学习和权限错误处理。进程内mock必须标出来，不能冒充真实连接。

## 4. 打开小型参考项目

它不是我自己刚做的小Demo。能看见为何现在读、核心范围、跳过什么、正常链/失败链、要比较的问题与复制Prompt。外部AI在学习当时自行找代码，不要求固定旧文件。

Pi/browser-use只是合适候选；已有其他更匹配项目时可以替换，不需要同时学两者。

## 5. 打开专项与成熟工程阶段

专项教程有具体章节范围，解释哪些是已学复习、哪些是新增。大型项目只读我需要的部分；不是整仓通读，也不是只有GitHub链接。

能回答“学完这些教程后，我带着什么问题进入这个成熟项目”“研究后哪些机制适合迁回自己的项目”。

## 6. 刷新与历史

退出重登录后，阶段、多个unit、完整项目卡和Prompt仍在；读取不生成第二个Plan、不收费。旧v6.8真实Plan没有被悄悄改成新版本。

## 7. 两个反例检查

“只想学MCP”的计划不应强塞整套RAG和大小项目。

“已有NodeAPI学部署”的计划不应让我重写Python服务；平台/DB未选的实际操作应明确待选。

## 结果记录

每个问题记录：页面/阶段名称、实际看到什么、期待什么、截图或原文。分别判断课程安排、资料范围、UI表达、模型生成还是数据缺口，不一律要求重做整个项目。

只有你确认这些内容足够清楚、愿意按它开始学，才算本轮用户体验接受。技术PASS不替代这一决定。
