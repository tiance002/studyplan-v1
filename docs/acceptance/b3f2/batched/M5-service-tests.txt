process which writes to PostgreSQL must be run **outside the tool sandbox**. The

## 5. Known flaky socket tests (pre-existing baseline, recorded separately)

`backend/tests/e2e/test_b2v_socket_counterexamples.py` re-runs four B2-V
regression scenarios over a real localhost socket (uvicorn in a thread) instead
of the in-process TestClient. They fail with:

    AssertionError: {"detail":"Not Found"}  assert 404 == 200

Evidence that this is pre-existing and not introduced here:

- On the untouched baseline (HEAD 2bd8445, git worktree) the same command
  `pytest test_b2v_http_end_to_end.py test_b2v_socket_counterexamples.py`
  also fails exactly these 4 tests (4 failed, 24 passed).
- They pass when the whole suite happens to run in one order and fail in another
  (both outcomes observed on this branch), i.e. they are order/timing dependent.
- Historical observation (RLS root-cause inference withdrawn by B3-F2.1): the run row IS committed (`status='waiting_user'`,
  `project_id='b2v_p1'`, verified via the migrator role) but the immediately
  following `GET /runs/{id}` returns 404. `ai_runs` has FORCE ROW LEVEL SECURITY
  with policy `project_id = current_setting('app.project_id')`. Row existence and
  that policy did not prove the GET reached this API or identify an RLS race.
  B3-F2.1 proves an environment-proxy leak in the localhost test client and an
  exact symptom reproduction; see ../hardening/Socket-visibility.md. Historical
  failure counts above remain unchanged as historical evidence.

Per the handoff these are recorded against the existing baseline and are not
counted as a green pass.

## 6. Defect found and fixed while validating Task 5

`planning_batches.recursion_limit()` under-counted the real `StateGraph` super-steps
(it assumed 2 per batch: generate+validate, but each batch is generate+validate+
advance = 3, minus one for the last batch of each phase). A full 9-stage Agent run
therefore hit `GraphRecursionError: Recursion limit of 50 reached` and the run was
reported as `planning_failed` instead of `waiting_user`.

- Surfaced by: `test_b3f2_learning_route.py::test_mock_http_provider_full_pg_graph_and_ledger`
  (the only test that drives the *real* LangGraph executor; the interpreter path
  used `max_steps=400` and hid the divergence).
- Fix: `recursion_limit()` now derives from the frozen batch counts with the
  correct per-batch cost (generate+validate+advance, minus one per phase), plus
  2 per bounded repair, plus a fixed margin. Verified: the test now reaches
  `waiting_user` with exactly 19 requests.

## 8. Design-revision conformance (Task 5 items)

- New Runs uniformly use `b3f2-batch-v1` (`config.graph_version` default; the
  service guard rejects any other configured value instead of silently converting).
- Protocol + model-config descriptor + task manifest are frozen at enqueue
  (`_freeze_submission` → `freeze_manifest`, `SubmissionBinding`).
- Only same-protocol recovery is supported; `builder_for_version` refuses every
  other version (incl. `"1"`, `"planning-legacy-v1"`, `""`).
- Historical legacy Runs are never auto-upgraded or continued.
- Legacy-only routing, DTO conversions and compatibility tests were removed
  (`planning_executor` has no version routing; `test_legacy_checkpoint_compatibility.py`
  and `helpers/legacy_planning_checkpoint.py` deleted — git history retains them).
- Existing tests were updated to assert the new contract (request counts 3→5/19,
  task-link counts 1→2, `progress` in the run DTO) rather than deleted.
- `RunProgress`, state transitions and the new HTTP default protocol are complete.
